# RC

Remote device control plane for OhRats Technologies.

## Rules

- Keep the control plane small and observable.
- Treat disconnects, stale devices, and interrupted processes as normal states.
- Never store agent private keys or plaintext auth/enrollment tokens server-side.
- Passkeys are the human credential; there is no email/password or recovery flow. Human CLI login uses the passkey-backed browser authorization flow.
- Public account signup is an explicit deployment policy, disabled by default. When enabled, require a configured Cloudflare Turnstile Managed widget and successful server-side Siteverify validation before issuing the signup WebAuthn ceremony. Never replace protected first-instance setup with public signup, and do not add a second CAPTCHA/rate-limit system inside RC when Cloudflare is the managed-service abuse boundary.
- API keys are automation proof-of-possession credentials only. Generate their Ed25519 private keys client-side, store only public keys/scopes server-side, and sign each request including method, path/query, timestamp, nonce, and body SHA-256. Never reintroduce bearer API tokens. Keep key management visible under the API route and do not offer API keys as browser-login substitutes. Key administration itself requires a human browser session.
- Remote MCP lives at `/mcp` and is a thin adapter over RC domains, not a parallel control plane. Keep OAuth/grants/protocol/tool adapters under sibling `src/mcp/` modules with a small tool registry. Observe is read-only; Terminal is explicit. Execution-capable grants require a fresh passkey ceremony, explicit device selection, Owner authority, a maximum ~30-day lifetime, and inclusion in RC Lock before the Node will execute them. OAuth access tokens are short-lived and resource-bound; refresh tokens rotate. Do not expose device update/removal through MCP v1.
- Shared visual primitives use content-fingerprinted immutable URLs under `https://assets.ohrats.party/assets/`.
- Follow cross-product UI guidance in `../handbook/design/ui.md`; when review feedback generalizes, promote it there/shared UI instead of keeping a one-off local fix.
- Product CSS must use existing `--or-*` tokens; do not invent a parallel design system.
- Keep browser source typed under `web/`. Bun remains the runtime and bundler; do not add a custom asset pipeline or untyped `public/js` tree.
- API routes are versioned under `/api/v1`.
- Persist server state under `/data` in production.
- Keep every maintained source file under 300 lines. Split by responsibility before a file reaches that size.
- Global navigation uses the persistent sidebar. Keep brand/collapse chrome pinned while the navigation tree scrolls. Workspace folders disclose device children; the folder click itself does not navigate. Disclosure height animates rather than snapping. Keep child lists bounded. Workspace and device rows share one composite row/context-menu treatment; device depth comes from inline-start indentation. Keep workspace enrollment/access/audit plus rename/delete lifecycle actions in the workspace ellipsis, and device rename/update/delete in the device ellipsis. Edit simple names directly in their labels and dismiss menus on outside interaction/Escape. Do not add workspace overview/detail pages that only duplicate sidebar functionality.
- Workspace creation is inline in the sidebar folder list. Enter creates; Escape/blur cancels. Do not reintroduce `/workspaces` or `/workspaces/new` HTML pages unless they gain materially distinct product functionality.
- Device presence is always visible in the hierarchy and uses shared semantic positive/negative state tokens. Long child labels may marquee only while hovered/focused and only when measured overflow exists; keep the row itself still and respect reduced motion.
- Device/workspace deletion is confirmed in the shared semantic sidebar dialog and then uses the authenticated DELETE API. Do not reintroduce dedicated delete-confirmation pages for these lightweight lifecycle actions.
- Keep the device page operationally minimal: platform + identity/presence, host + Node version, compact header rename/terminal/delete actions, and process history. Do not duplicate RC/server and Node versions when they are normally equal; surface version mismatch through the contextual update action. Do not reintroduce the custom command/cwd form in the device UI; explicit commands belong to API, CLI, or MCP Terminal.
- Legacy plaintext PTY history renders through xterm's terminal parser so ANSI/OSC/cursor sequences are interpreted rather than exposed as text. New encrypted processes are metadata-only on RC: never persist command/cwd/stdin/stdout/stderr or reconstruct an encrypted transcript server-side. A Node may buffer a bounded encrypted-process backlog in memory for authorized reconnect, but completed encrypted transcript contents are intentionally not hosted history.
- Standalone collection pages use compact header creation controls rather than permanent creation sections when the task is short. API key creation is a header-plus modal with a normal `/api/keys/new` form fallback; the one-time key is revealed immediately with the shared copy control.
- A detail-page header may repeat the immediate identity/lifecycle actions that are useful while already viewing that object (for example device rename/delete) even when the persistent sidebar also exposes them contextually. Keep the action set compact and reuse the same underlying operation/dialog rather than creating a second workflow. Account deletion uses the shared centered delete dialog. Native dialogs must remain explicitly centered despite the shared universal margin reset.
- Account display-name edits happen directly in the page title. Account deletion removes the account, deletes every workspace where that account is an Owner, leaves non-owned workspaces through membership cascade, preserves surviving historical attribution as `Deleted account`, and returns to protected setup when no human accounts remain.
- Top-level collection pages use one page title (`Devices`, `API`, `MCP`) without repeating the same noun as an eyebrow. Detail/workflow pages may use an eyebrow when it contributes object/context information such as `DEVICE` or `WORKSPACE / ACCESS`.
- Device-list platform marks are based on operating-system platform, not CPU architecture. Keep macOS/Linux/Windows marks on the same normalized monochrome canvas and let shared CSS color them through `currentColor`; architecture remains textual metadata.
- Authenticated routes are ordinary server-rendered URLs. Do not require client-side routing for navigation. JavaScript may enhance individual pages but must not own primary page rendering.
- Prefer normal links, forms, POST/redirect flows, and server-rendered snapshots. JavaScript is reserved for capabilities that inherently require it or materially benefit from live enhancement.
- Keep authenticated pages visually flat: natural sections, typography, rows, and dividers. Do not turn every section into a bordered panel/card.
- Browser live state and WebRTC signaling use the authenticated WebSocket. Browser/CLI interactive control prefers a direct WebRTC DataChannel after the Node-authorized control handshake and uses the encrypted WebSocket relay when the direct transport cannot be established or later becomes unavailable. HTTP remains for snapshots and ordinary CRUD. Do not reintroduce timer polling or make hosted RC the mandatory browser/CLI data plane.
- The device and human CLI share the `rc` binary. Keep the product name `RC`; OhRats is established by the product domain and company mark rather than repeated in the product name.
- Normal install/enrollment starts the Node as a per-user background service. `rc run` is the foreground/debug path, not a required second terminal in the normal setup flow.
- Device removal is available from the web, `DELETE /api/v1/devices/:id`, and `rc device delete`. Locked nodes erase local enrollment only after an owner-authorized encrypted `node.remove`; deleting the server record alone must never erase locked local state.
- Keep the product model `User → Workspace → Device → Process`. Do not add fleets or browser shell-session wrappers without a concrete need.
- Remote processes are byte-stream processes with an optional terminal attachment. `rc shell` and the browser terminal request a PTY; non-interactive execution such as `rc run` uses separate binary-safe stdin/stdout/stderr streams. Keep this primitive generic so SSH/SFTP/rsync can build on it without filesystem-specific Node RPCs.
- SSH compatibility uses stock OpenSSH `sshd` in the RC gateway container, not a JavaScript SSH implementation and not an SSH daemon on Nodes. Password/keyboard auth and forwarding are disabled. `AuthorizedKeysCommand` maps registered public keys to a forced RC bridge; generated OpenSSH config sends the full immutable RC device ID and uses `rc ssh-proxy` over the public WebSocket endpoint so client networks do not need outbound SSH ports. Keep device names out of routing authority.
- Remote processes are at-most-once. If execution becomes ambiguous after disconnect/restart, mark it lost instead of replaying it. RC Node shutdown, crash, and update must tear down every remote process tree; never leave detached remote work behind.
- RC Node authentication uses a server-issued one-time challenge signed by the device Ed25519 identity. Never put reusable signatures or authentication secrets in WebSocket URLs.
- RC Node/CLI releases are published by GitHub Actions from version tags. Treat the published GitHub Release as the release trust boundary. `install.sh` and Node updates download GitHub Release assets directly, verify the selected binary SHA-256 and reported version, and refuse downgrades. Do not make the RC runtime build, proxy, or bundle Node binaries.
- RC Lock is enforced locally by the Node. Its persisted authority snapshot owns member roles, passkey credential public keys, API signing public keys/scopes, and active execution-capable MCP grant hashes. First initialization is TOFU from the currently trusted instance and may never overwrite an existing lock. Every later snapshot must be signed by an existing Owner using a passkey-authorized control key; server database state alone is not authority. Accepting a new snapshot invalidates every live encrypted control session so removed/demoted identities must reopen against the new Node-local authority.
- Human browser/CLI control grants default to 30 days, but each live browser/CLI control connection uses fresh X25519 client and Node ephemeral keys. Mix those with the Node's pinned static X25519 key via HKDF-SHA256 and encrypt control frames with AES-256-GCM. The Node's Ed25519 identity signs the live handshake. Keep this RC encryption inside both WebRTC and relay transports until a separately reviewed transport-authentication change replaces it. Do not send browser/CLI process commands, process streams, signals, node updates, or node removal outside this encrypted Node-verified channel. MCP Terminal and gateway-terminated SSH are deliberate transport exceptions: their command/output plaintext transits RC memory and must never be persisted. Nodes still independently verify the supplied passkey-backed execution authority before starting a process.
- A locked Node must preserve local enrollment and RC Lock state if the server forgets or deletes its device record. Only an owner-authorized encrypted `node.remove` or explicit local uninstall may erase locked state.
