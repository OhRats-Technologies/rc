# OhRats RC

Remote control for your machines.

## Run

```sh
docker build -t rc .
docker run --rm -p 3000:3000 -v rc-data:/data rc
```

Open `http://localhost:3000` and create the first account.

The web UI is server-rendered React/TSX under `web/server/` with small progressive-enhancement modules under `web/client/`. Bun builds those modules and product CSS into content-hashed `/assets/*` files; ordinary navigation and CRUD do not depend on a client-side router.

The device-side program and human CLI are both **OhRats RC Node** (`ohrats-rc`). Running it with no arguments prints help. `enroll TOKEN` performs one-time device enrollment. Before RC Lock exists, enrollment can discard a stale local identity only when RC confirms the old device is gone; after a Node is locked, a server-side 404 never erases local enrollment or lock state. Locked removal must arrive through an owner-authorized encrypted control session, or be performed explicitly with local uninstall. The installer registers an enrolled node as a per-user background service (LaunchAgent on macOS, user systemd service on Linux where available), so normal enrollment does not require keeping `ohrats-rc run` open in another terminal. `service` manages that background node; `run` remains the foreground/debug path. `status` shows local/remote state, `update` replaces the node binary, `config` manages node defaults, and `uninstall` stops/removes the service, server registration, local state, and installed binary. For human use, `login` opens RC in the browser for passkey-backed CLI authorization, then `devices`, `shell DEVICE`, `run DEVICE -- CMD`, `actions`, and `action run` use that saved CLI session and its local control key. `logout` revokes the hosted session. `RC_API_TOKEN` / `--token` accepts a proof-of-possession API signing key for automation. State, device pins, control keys, config, service logs, and the protected CLI session live under `~/.config/ohrats-rc`.

The product model is `User → Workspace → Device → Process`, with saved `Action` definitions scoped to a workspace and executed through the same Process system. Devices belong directly to one workspace. There are no fleet or browser-session abstractions.

Passkeys are the human sign-in method. Browser and human CLI sessions default to 30 days. The first control action on a browser profile or a new CLI login creates a local Ed25519 control identity and asks the passkey to authorize its public key for up to 30 days; reconnecting terminals then use fresh transport keys without another passkey touch while that grant is valid. API keys live under `/api` and are scoped proof-of-possession signing credentials only (`read`, `execute`, `manage-devices`, `manage-workspaces`). RC stores an API key's public key, never its private signing key, and every API request signs its method, path/query, timestamp, nonce, and body SHA-256. Replayed nonces are rejected. API-key administration requires a human browser session and browser JavaScript so the private key can be generated client-side and revealed once.

Workspaces have three roles: **Owner** manages access, workspace settings, Actions, and device lifecycle; **Operator** can open terminals and run Actions; **Viewer** can inspect inventory, Actions, and audit metadata without process output or execution. A workspace may have multiple owners and RC will not allow its last owner to leave/demote themselves.

The persistent sidebar is also the workspace control surface. Workspace folders only expand/collapse their device children; the ellipsis menu owns enrollment, Actions, access management, audit history, rename, and deletion. New workspaces are created inline from the sidebar `+`, so there is no separate workspace overview/detail/new page. Device rows use the same treatment with live red/green presence and contextual rename/update/delete actions.

Account names can be edited directly in the account page title. Account deletion removes credentials and memberships, deletes every workspace the account owns, leaves workspaces it does not own, preserves retained attribution in surviving workspaces under `Deleted account`, and returns RC to protected setup when the final human account is removed.

The browser uses ordinary HTTP for metadata snapshots/CRUD plus one authenticated WebSocket that relays live events and opaque encrypted control frames. Execution authority is enforced by the Node, not by the RC server. Each live browser/CLI control connection mixes the Node's pinned static X25519 transport key with a fresh client X25519 key and a fresh Node X25519 key, derives an AES-256-GCM key with HKDF-SHA256, and authenticates the handshake with the Node's Ed25519 identity plus the client's passkey-backed or API proof-of-possession key. WebSocket frame sequence numbers are authenticated and strictly monotonic. The RC server therefore routes terminal commands, stdin, signals, stdout/stderr, and lifecycle commands without possessing their plaintext. A later compromise of the Node's long-term transport key alone is not enough to decrypt recorded sessions because the fresh Node ephemeral contribution is not retained.

The browser application is part of the trusted client computing base because RC serves its JavaScript. A fully compromised web server that replaces that code while an already-authorized user visits could ask the browser-held non-extractable control key to sign operations as that user. RC Lock prevents the server/database from manufacturing those signatures by itself, and the signed `ohrats-rc` CLI avoids this web-code-delivery dependency. Do not describe the browser path as code-transparency or malicious-web-server resistant without an independently pinned client.

RC Lock persists the workspace authority snapshot locally on each Node. The snapshot contains member roles, passkey credential public keys, and authorized API signing public keys/scopes. The first lock initialization for an enrolled Node is a trust-on-first-use bootstrap from the currently trusted RC instance; it never overwrites an existing lock. Every later authority change must be signed by a client whose 30-day passkey grant verifies against an Owner already present in the Node's previous snapshot. RC may relay a proposed snapshot but cannot manufacture an accepted Owner, Operator, Viewer, or API execution key by changing its database alone. When a Node accepts a new authority snapshot it invalidates all live encrypted control sessions immediately, so removed/demoted identities and revoked API keys must reopen against the new Node-local authority. The access page reports a lock change as synchronized only after Nodes reconnect/report the accepted lock hash.

Hosted encrypted processes retain metadata only: process ID, device, creator, start/end state, dimensions, exit code/signal, and timestamps. Commands, cwd, stdin, and terminal output are not persisted in SQLite for encrypted processes. During a short client/control-plane disconnect, the Node keeps a bounded in-memory encrypted-process backlog and delivers it only after an authorized client reattaches; completed encrypted transcript contents are intentionally not recoverable from RC history. Saved Action definitions remain workspace metadata stored by RC, but executing an Action sends its command to the Node inside the same encrypted control channel.

Node authentication is replay-resistant: the server issues a short-lived one-time challenge and the Node signs the challenge, method, and path with its local Ed25519 identity before WebSocket/status/unregister requests. RC 0.8 Nodes reject plaintext process, update, and remove commands unconditionally; a missing/uninitialized RC Lock can make control unavailable but cannot make the Node fall back to server-authorized execution. Hosted-service hardening also applies application rate limits, restrictive browser security headers, configurable account/device/process quotas, short invite/enrollment lifetimes, 30-day human sessions/control grants, and a non-root production container.

Node updates are release-signed independently of the RC runtime. The Node embeds only the OhRats Ed25519 release public key, verifies the signed `release.json` manifest, checks the selected artifact SHA-256 and reported version, and refuses signed downgrades before replacing itself. The release private key is kept outside the repository and runtime infrastructure.

Owners can save commands as **Actions**. Actions may require confirmation and can run on one or more selected devices; each device execution creates a normal metadata Process while the command and live terminal stream travel only through the encrypted control channel. Action execution therefore shares permissions, status, and completion behavior without creating a second job system or retaining encrypted terminal contents on RC.
